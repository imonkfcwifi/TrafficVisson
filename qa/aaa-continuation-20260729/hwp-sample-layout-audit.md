# TrafficVisson 실사 보고서 HWP/HWPX 레이아웃 감사

작성일: 2026-07-29  
상태: 실제 사용자 제공 문서의 **읽기 전용 구조 감사**. TrafficVisson이 이 문서를 수정하거나 완성 보고서를 생성했다는 증거가 아니다.

## 1. 감사 입력과 무결성

|---|---:|---|---|

| `sample/4분기 점검 내용 정리.hwpx` | 863,683,207 bytes | `bbdd61a6ef192a957a5e9480b0c2eedbfe956dd184abd5d76f59474254941539` | 원본 HWPX, 읽기 전용 |
| `sample/3분기 점검 내용 정리.pdf` | 6,141,037 bytes | `9a4b3f093b9fd8c320c55b1b80ac29a359a32c458f814ef6f3bc1cb2763c1e89` | 한/글 2024로 렌더된 48쪽 A4 PDF |

시각 감사는 두 PDF의 **48쪽 전 페이지 접촉 시트**와 각 문서의 1, 2, 24, 47, 48쪽 고해상도 렌더를 함께 사용했다. 렌더 근거는 `tmp/pdfs/`에 보존했다.

- `tmp/pdfs/3q-all-48-contact.png`
- `tmp/pdfs/4q-all-48-contact.png`
- `tmp/pdfs/3q-page-{01,02,24,47,48}.png`
- `tmp/pdfs/4q-page-{01,02,24,47,48}.png`

이 감사로 원본 양식의 전 페이지 구조와 반복 패턴은 확인했지만, TrafficVisson이 만든 출력물의 보존 상태를 증명한 것은 아니다. 최종 제품에서는 편집 결과를 다시 48쪽 전부 렌더하고 기준 템플릿과 자동·육안 비교해야 한다.

HWPX ZIP의 `Contents/section0.xml`도 원본을 풀거나 수정하지 않고 읽기 전용으로 집계했다.

| 구조 | 3분기 | 4분기 |
|---|---:|---:|
| `section0.xml` 문자 수 | 5,464,293 | 5,587,216 |
| 문단 | 6,691 | 6,776 |
| 표 | 72 | 72 |
| 표 셀 | 6,353 | 6,456 |
| 그림 개체 | 147 | 173 |
| 명시적 페이지 나눔 | 47 | 46 |
| 이름 필드 | 0 | 0 |
| 책갈피 | 0 | 0 |

두 실제 양식에는 이름 필드와 책갈피가 없다. 따라서 현재의 `field`·`bookmark` 대상만으로는 이 문서를 자동으로 채울 수 없다. HWPML 표·셀·사진 슬롯의 안정적인 구조 주소와 기준 스냅샷을 생성하는 매퍼가 별도로 필요하며, 이를 구현하기 전에는 “사용자 양식 지원 완료”로 판정하지 않는다.

## 2. 실제 문서에서 확인한 레이아웃 계약

### 2.1 첫 장: 점검 결과 요약표

- A4 세로 한 페이지 안에 평가 항목, 등급 또는 상태, 서술형 점검 의견이 들어가는 표가 있다.
- 셀별 테두리, 정렬, 문단 간격, 줄바꿈이 문서의 정보 계층을 만든다.
- TrafficVisson은 첫 장을 자유 형식 AI 문장으로 다시 그리지 않고 기존 표 주소와 서식을 보존해야 한다.
- 자동 입력은 `Incident` 및 `MaintenanceAction`에서 검증된 요약만 대상으로 하며, 사용자가 확정하지 않은 후보를 점검 결과로 승격해서는 안 된다.

### 2.2 사진 대지: 2열 증거 그리드

- 대표 사진을 좌우 2열로 배치하고 각 사진 아래 또는 인접 영역에 설명 문구를 둔다.
- 모든 셀이 사진으로 채워지는 것은 아니다. 일부 빈 셀은 대각선 표시 또는 기존 빈 슬롯 표현을 유지한다.
- 사진 비율과 셀 높이가 일정하며, 원본 사진을 억지로 늘리기보다 슬롯 안에서 비율을 보존해 맞춰야 한다.
- 캡션은 최소한 사건 유형, 위치 또는 방향, 관찰 내용, 권장 조치를 연결해야 한다.
- 같은 사건의 전후 프레임을 별도 사건처럼 중복 삽입하지 않고 시간축 병합 결과의 대표 근거와 보조 근거로 묶어야 한다.

### 2.3 반복되는 페이지 구조

- 두 문서 모두 정확히 48쪽 A4 세로 문서다.
- 1·3·5…47쪽은 노선·현장 식별 정보, 평가 항목과 네모 표시, 자문·점검 의견 및 서명 영역을 가진 점검표 계열이다.
- 2·4·6…48쪽은 좌우 2열 사진 대지 계열이다. 페이지별 사진 수는 내용에 따라 달라지지만 기존 슬롯·캡션·빈칸 구조는 유지된다.
- 사진이 없는 슬롯에는 대각선 표시 등 기존의 빈 슬롯 표현이 남아 있으며, 자동 편집기가 이를 임의로 사진 영역으로 재사용하면 안 된다.
- 머리말·꼬리말, 페이지 번호, 표 경계, 사진 슬롯과 캡션 정렬이 페이지마다 반복된다.
- 기존 빈 슬롯과 페이지 나눔은 의미 있는 레이아웃 요소이므로 AI가 임의로 삭제하거나 재배치하면 안 된다.
- 삽입 후 사진 누락, 표 잘림, 캡션 고아, 페이지 넘침, 머리말·꼬리말 손상, 빈 페이지 증가를 검사해야 한다.

### 2.4 전 페이지 수용 불변식

TrafficVisson의 HWPX 편집 결과는 다음 조건을 모두 만족해야 한다.

1. 페이지 수는 사용자가 승인한 `DocumentEditPlan`에서 의도적으로 변경하지 않는 한 48쪽을 유지한다.
2. 홀수 쪽의 점검표 계열과 짝수 쪽의 사진 대지 계열이 뒤바뀌거나 한쪽씩 밀리지 않는다.
3. 네모 표시는 기존 평가 항목 셀 안에서 같은 방식으로 적용되고, 다른 행·열 또는 서술 셀로 이동하지 않는다.
4. 사진은 원래 사진 슬롯에만 들어가며 좌우 2열, 종횡비, 캡션 대응 관계를 보존한다.
5. 정확한 노선·위치·자문 또는 점검 의견은 해당 페이지의 기존 셀 주소에 들어가고, 다음 페이지로 넘쳐 새 빈 페이지를 만들지 않는다.
6. 빈 슬롯과 대각선 표시는 계획에 명시된 사진 삽입 대상이 아니면 그대로 보존한다.
7. 적용 후 재열기와 48쪽 전 페이지 렌더가 모두 성공하고, 누락·겹침·잘림·페이지 넘침 검사 결과가 저장되어야만 `validated`로 승격한다.

## 3. 표본에서 확인한 유지보수 사건과 표준 유형 매핑

아래 매핑은 문서 표본을 TrafficVisson의 표준 12유형 계약에 연결하기 위한 **보고서 템플릿 매핑**이다. 실제 사건 라벨 또는 모델 성능 증거가 아니다.

| 문서 표본의 표현 | TrafficVisson 표준 유형 | 권장 조치 예 |
|---|---|---|
| 낙하물·중앙분리대 주변 이물질 | `road_debris` | 긴급 제거 또는 청소 후 안전 확인 |
| 도로 파임 | `pothole` | 응급 보수 후 단면 복구 검토 |
| 노면 파손 | `road_surface_damage` | 균열·박리 범위 확인 후 보수 |
| 노면 색깔유도선 재도색 필요 | `colored_guidance_faded` | 색깔유도선 재도색 |
| 일반 차선 소실·마모 | `lane_marking_faded` | 차선 재도색 |
| 삭초 필요·포장 이음부 식생 | `roadside_mowing_required` | 삭초·제초·전정 |
| 표지판 식생 가림 | `sign_vegetation_occlusion` | 가림 식생 제거·가지치기 |
| 터널명 식생 가림 | `tunnel_name_occlusion` | 명판 시야 확보를 위한 전정 |
| 표지판 파손·문자 탈락 | `sign_damage` | 표지판 복구·교체 |
| 중앙분리대·충격흡수시설 파손 | `median_barrier_damage` 또는 `other` | 시설 형식에 맞는 복구·교체 |
| 터널명 식별 | `tunnel_identity` | OCR 원문과 위치 기준 자료 검증 |

표본에는 불법주정차, 스키드마크, 터널 조도 저하, 터널 LED 고장, 배수시설 청소, 과속방지턱 필요처럼 표준 12유형 바깥의 항목도 있다. 이를 기존 유형에 억지로 합치지 않고 `other` 운영 확장으로 보존하며, 반복 수요와 라벨 기준이 확정된 뒤 별도 계약으로 승격한다.

## 4. 구현 계약

### 4.1 미리보기

미리보기 응답은 다음 값에 서버 측으로 결속되어야 한다.

- `project_id`
- 실제 선택 문서의 정규 경로·파일 ID·크기·수정 시각·SHA-256
- 정규화된 `DocumentEditPlan`의 SHA-256
- 대상 표·셀·문단·사진 슬롯 요약
- 발급 시각과 만료 시각

미리보기는 원본 문서를 변경하지 않는다. 적용은 동일 값에 결속된 단회 승인 토큰으로만 허용하며, 교차 프로젝트 사용, 만료, 재사용, 문서 변경, 계획 변경을 COM 실행 전에 거부한다.

### 4.2 결정적 편집

- LLM은 허용된 스키마의 `DocumentEditPlan`만 만든다.
- 실제 문서 쓰기는 허용 작업을 구현한 결정적 COM 편집기가 수행한다.
- 원본은 읽기 전용으로 유지하고 같은 디렉터리의 새 출력 파일에만 저장한다.
- 텍스트·표 셀·사진·지도 삽입 작업은 실제 HWPML 대상 주소와 슬롯 종류를 검증해야 한다.
- 공유용 결과에는 비식별화가 완료된 사진만 사용할 수 있다.
- 적용 전후의 문서·계획·근거 해시와 작업 결과를 감사 로그에 남긴다.

### 4.3 저장 후 검증

저장 성공만으로 완료 처리하지 않는다.

1. 출력 HWP/HWPX를 다시 연다.
2. 예상 문단·표·셀·사진 개수와 삽입 대상이 존재하는지 확인한다.
3. PDF 또는 페이지 이미지로 전 페이지를 렌더한다.
4. 기준 템플릿과 페이지 크기·머리말·꼬리말·표 위치를 비교한다.
5. 사진 누락, 0바이트 이미지, 캡션 고아, 표 잘림, 겹침, 페이지 넘침, 비정상 빈 페이지를 검사한다.
6. 실패 시 최종 보고서로 게시하지 않고 작업본과 오류 근거만 보존한다.

따라서 이 감사는 TrafficVisson의 기본 보고서와 사용자 양식 지원에 필요한 실제 구조를 확정했지만, HWP/HWPX 보고서 기능의 완료 증거는 아니다.

## 6. P0 안전 수직 슬라이스 구현 결과

실제 COM을 실행하거나 원본·열린 한/글 문서를 변경하지 않고 다음 경계를 구현했다.

### 6.1 정확 표본 baseline

`app.hwpx_sample_layout`은 파일명만 믿지 않고 3·4분기 HWPX의 실제 SHA-256을 기준으로 표본을 식별한다. 다음 값이 모두 감사 baseline과 일치해야만 표본 구조 preview를 만든다.

| 불변식 | 3분기 | 4분기 |
|---|---:|---:|
| 렌더 기준 페이지 | 48 | 48 |
| 점검표/사진 페이지 쌍 | 24 | 24 |
| section | 1 | 1 |
| 표 | 72 | 72 |
| 셀 | 6,353 | 6,456 |
| 그림 | 147 | 173 |
| 점검표 고정 그림 | 24 | 24 |
| 기존 사진 그림 | 123 | 149 |
| 명시적 페이지 나눔 | 47 | 46 |
| field / bookmark | 0 / 0 | 0 / 0 |
| 구조 target summary SHA-256 | `88238874c4508480d620493112a2b46fac96c311999f57f3df8f9582a5e1a7f5` | `582d835ccf71aaf04f9a8ee42dbc2e5c508c9cde4b21bc8d9ed175d789ec8f4a` |
| 약한 사례 index manifest SHA-256 | `4d06ede9c320090c1aec107eb9c41877ea2b9d924e2d3724821dbe42f520694f` | `31f3e04d5fecf64078afebf4bc21312d701dadc3eac5f2302a4bb4b236247041` |

한 쌍마다 표가 정확히 3개씩 반복된다. `3n`, `3n+1` 표는 홀수 점검표 쪽, `3n+2` 표는 짝수 사진 대지 쪽으로 결속한다. 이 규칙은 PDF 48쪽 전 페이지 감사와 정확한 HWPX 구조 hash를 함께 고정한 것이다.

중요하게도 4분기 문서는 48쪽이지만 명시적 페이지 나눔은 46개다. 따라서 page-break sequence를 렌더 페이지로 오인하지 않는다. 새 매퍼는 마지막 `table_index=71` 사진 target을 24번째 쌍의 짝수 쪽, 즉 48쪽으로 결속하며 이 동작을 실제 표본 회귀 테스트로 고정했다.

### 6.2 서버 소유 DocumentEditPlan preview

새 읽기 전용 endpoint:

`POST /projects/{project_id}/hwp/sample-layout-preview`

이 endpoint는 COM을 호출하지 않고 다음을 검증한다.

1. exact sample SHA와 전체 구조 baseline 일치
2. `DocumentEditPlan.document_snapshot_id`와 서버가 만든 구조 snapshot 일치
3. 모든 operation target이 현재 문서의 정확한 `hwpx-cell-*` 또는 `hwpx-picture-*` target인지 확인
4. operation별 table index, 1~48쪽 page number, 점검표/사진 대지 종류, 행·열과 source ref 결속
5. 같은 target 중복 수정 거부
6. `add_table_row`, `fill_text`, `inherit_target` 거부
7. 점검표 쪽 고정 그림을 사건 사진 슬롯으로 사용하는 계획 거부
8. 기존 사진 target 중 좌우 2열 격자 밖 target 거부

응답은 document/target/baseline PDF/약한 사례 index/plan/layout-contract SHA-256과 선택된 target binding만 반환한다. 따라서 48쪽 시각 baseline과 초기 사례 DB provenance도 같은 preview에서 추적할 수 있다. 원본 경로와 인증 정보는 반환하지 않는다.

### 6.3 거짓 성공 차단

현재 응답 상태는 항상 다음과 같다.

- `state=validated_structure_preview_apply_blocked`
- `apply_eligible=false`
- `output_rendered_page_count=null`
- `output_render_validation_status=not_run`

차단 사유도 고정 계약으로 모두 반환한다.

1. `exact_hwpml_target_writer_not_implemented`
2. `semantic_cell_role_map_not_approved`
3. `output_reopen_and_48_page_render_validation_not_implemented`

표본 SHA가 확인된 문서는 기존 field/bookmark COM preview 경로로 우회할 수 없다. 또한 `HwpApprovalRegistry`가 방어적으로 같은 SHA의 적용 토큰 발급을 거부한다. 따라서 실제 HWPML target writer와 저장 후 48쪽 전 페이지 렌더 검증이 구현되기 전에는 페이지 누락, 페이지 수 변화, 슬롯 오배치를 `applied` 또는 `validated`로 저장할 수 없다.

### 6.4 회귀 증거

실제 COM은 호출하지 않았다. 가짜 COM 서비스는 표본 preview 전후 호출 횟수가 0인지 검증했다.

```powershell
python -m pytest .\tests\test_hwpx_structure.py .\tests\test_hwpx_weak_cases.py .\tests\test_weak_case_catalog_api.py .\tests\test_hwp_com.py .\tests\test_hwp_approval.py .\tests\test_hwp_api.py .\tests\test_hwpx_sample_layout.py -q
```

결과: `82 passed, 1 skipped in 16.57s`.

skip 1건은 실제 Windows COM 종단 환경이 필요한 기존 테스트다. 이번 수직 슬라이스는 의도적으로 COM 적용, 출력 HWPX 재열기, 48쪽 렌더 생성·비교를 수행하지 않았다.

전체 Bridge 회귀도 별도로 실행했다.

```powershell
python -m pytest -q
```

결과: `601 passed, 2 skipped in 114.19s`. 두 skip은 환경 의존 테스트이며 실패는 0건이다.
