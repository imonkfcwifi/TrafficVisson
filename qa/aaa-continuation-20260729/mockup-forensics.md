# TrafficVisson 디자인 포렌식

작성일: 2026-07-29  
범위: `Pretendard와 리퀴드 글래스 디자인` 폴더 전체  
작업 성격: 읽기 전용 분석. 이 문서 외 구현 코드는 수정하지 않았다.

## 0. 결론

디자인 폴더의 자료는 하나의 동일한 시안이 아니라 역할이 다른 세 층이다.

1. `uploads/pasted-1785143633633-0.png`는 최종 제품이 따라야 할 **시각 언어와 화면 밀도**의 기준이다.
2. `TrafficVisson Desktop.dc.html`과 `.thumbnail`은 9개 화면의 **정보 구조와 상호작용 의도**를 보여 주는 역사적 디자인 컴포넌트다.
3. `uploads/TRAFFIC_VISSON_MASTER_PLAN.md`는 기능 누락을 찾는 **완전성 체크리스트**로는 유효하지만, 파일 자체가 명시하듯 현재 구현 상태의 기준본은 아니다. 현재 상태 기준은 루트 `TRAFFIC_VISSON_MASTER_PLAN.md` v2.9다.

따라서 구현은 참조 PNG의 차분하고 비대칭적인 리퀴드 글래스 언어에, HTML의 9개 업무 화면과 루트 v2.9의 실제 기능 상태를 결합해야 한다. HTML을 그대로 제품에 넣거나, 1920×1080 고정 좌표와 원격 CDN 의존성을 복사하거나, 역사적 계획서의 목표형 문장을 구현 완료로 해석하면 안 된다.

가장 중요한 판정은 다음과 같다.

- 프로그램은 Windows Electron 창 전체를 사용하는 하나의 제품이어야 한다. 창 안에 다시 큰 웹페이지 프레임을 넣는 구조는 참조와도 맞지 않는다.
- 참조 PNG의 핵심은 “모든 카드가 유리”가 아니라, **저채도 청회색 바탕 + 불투명도가 충분한 소수의 유리 표면 + 한 개의 강한 포컬 카드 + 검은 CTA**다.
- 참조는 네 개의 같은 KPI 카드를 늘어놓지 않는다. 큰 카드, 중간 카드, 목록, 보조 카드가 명확히 다른 비중을 가진다.
- 최종 글꼴은 사용자 최신 지시와 루트 v2.9에 따라 **앱에 번들한 SUIT Variable**이다. HTML의 Pretendard CDN은 현재 폰트 기준이 아니다.
- 1280×720에서 문서 전체 스크롤 없이 현재 작업과 핵심 조작이 보여야 한다. 긴 목록만 경계가 분명한 한 곳의 내부 스크롤을 소유할 수 있다.
- HTML에 보이는 수많은 `cursor:pointer` 요소 중 실제 상태 변경이 연결된 것은 일부뿐이다. 제품 검증에서는 보이는 버튼이 아니라 실제 IPC·브리지·저장 결과로 동작 여부를 판정해야 한다.

### 파일 간 관계

- 참조 PNG는 TrafficVisson 화면이 아니라 금융 대시보드다. 따라서 텍스트나 기능을 복제하는 자료가 아니라 **비율, 재료, 위계, 밀도**를 추출하는 자료다.
- `.thumbnail`은 참조 PNG가 아니라 HTML 프로토타입의 미리보기다. 둘을 같은 소스 이미지로 취급하면 안 된다.
- HTML은 `support.js`가 `unpkg.com`에서 React 18.3.1과 ReactDOM을 불러와야 실행되는 디자인 도구 산출물이다. HTML 자체도 Pretendard와 JetBrains Mono를 외부 CDN에서 불러온다.
- 이 네트워크 의존성은 오프라인 Windows 제품의 런타임 설계가 아니다. 제품 코드는 기존 Electron/Vite 번들 구조를 계속 사용해야 한다.

## 2. 참조 PNG의 측정 가능한 시각 언어

아래 치수는 1200×900 원본의 평면화된 래스터에서 측정한 값이며, 안티앨리어싱과 그림자를 포함해 약 ±2~4px 오차가 있을 수 있다.

### 2.1 캔버스와 큰 그리드

| 항목 | 측정치 | 구현 의미 |
|---|---:|---|
| 전체 캔버스 | 1200×900 | 4:3 프레젠테이션 이미지이므로 앱 창 비율을 그대로 고정하지 않는다 |
| 외부 바탕 | `#E7ECF2` 근사 | 순백이 아닌 차가운 회청색 |
| 주 셸 | 약 x=60, y=60, w=1080, h=780 | 사방 60px 여백, 큰 단일 작업면 |
| 셸 그림자 범위 | 약 x=47..1152, y=47..849 | 약 13px 이상 번지는 낮은 채도의 그림자 |
| 왼쪽 작업 열 | 약 x=162..749, w=588 | 전체 업무 폭의 약 62% |
| 오른쪽 보조 열 | 약 x=792..1108, w=317 | 전체 업무 폭의 약 33% |
| 열 사이 간격 | 약 42px | 내부 카드 간격보다 큰 구조적 분리 |
| 카드 사이 기본 간격 | 약 12px | 조밀하지만 답답하지 않은 리듬 |
| 주 카드 반경 | 약 20~22px | 모든 작은 요소에 같은 큰 반경을 쓰지 않는다 |

참조의 핵심 비율은 `왼쪽 넓은 업무 영역 : 오른쪽 좁은 보조 영역 ≈ 65 : 35`다. 좌우가 같은 1:1 대시보드가 아니다.

### 2.2 카드 위계와 실측 영역

| 영역 | 대략적 좌표·크기 | 위계 |
|---|---|---|
| 잔액 히어로 | x=162, y=168, w=588, h=216 | 가장 큰 단일 포컬 카드 |
| 지출 통계 | x=162, y=396, w=290, h=191 | 보조 분석 |
| 재무 상태 | x=464, y=396, w=286, h=191 | 유일한 강한 파란 그래디언트 카드 |
| 예정 결제 | x=162, y=600, w=588, h=216 | 넓은 목록 카드 |
| 거래 목록 | x=792 부근, 상단부터 y≈166~486 | 경계가 약한 세로 정보 목록 |
| 빠른 송금 | x=792, y=600, w=317, h=216 | 보조 행동 카드 |

가장 중요한 특징은 카드의 크기와 역할이 다르다는 점이다.

- 한 개의 큰 포컬 카드가 화면을 잡는다.
- 보조 분석 카드는 그보다 작다.
- 목록은 넓고 낮다.
- 우측은 카드 벽이 아니라 정보 흐름과 한 개의 행동 카드로 구성된다.
- 모든 카드에 같은 그림자, 같은 강조색, 같은 제목 크기를 주지 않는다.

### 2.3 색과 재료

래스터에서 직접 얻은 대표 샘플은 다음과 같다. 합성된 이미지의 픽셀이므로 CSS 원색이 아니라 최종 보이는 색이다.

| 용도 | 근사 샘플 |
|---|---|
| 외부 바탕 | `#E7ECF2` |
| 셸의 청보라 영역 | `#A0B2DA`, `#8FA6DC` 계열 |
| 밝은 유리 카드 | `#CED9EB`, `#D4E0EE`, `#DCE3EB` 계열 |
| 강한 파랑 | `#6191FF` → `#6B95F7` |
| 보조 보라 | `#7661EC` |
| 검은 CTA 바탕 | `#110D0A` 근사 |
| 기본 문자 | 거의 검정, 약 `#0B0D12` 계열 |

표면 규칙:

- 유리는 완전히 투명하지 않다. 카드 내용 뒤 배경이 읽히지 않을 정도로 충분히 불투명하다.
- 테두리는 진한 회색선이 아니라 흰색에 가까운 1px 하이라이트다.
- 그림자는 검은 드롭섀도가 아니라 청보라 저채도 그림자다.
- 색상 강조는 화면 전체가 아니라 포컬 카드와 상태 칩 일부에 한정한다.
- 검은색 알약형 CTA가 가장 강한 행동 신호다.
- 그라디언트는 배경과 한두 개 핵심 카드에만 있다. 모든 카드에 무지개 그라디언트를 넣지 않는다.

### 2.4 타이포그래피

참조 PNG의 시각적 스케일:

- 제품/영역 제목: 약 20~24px, 500~650
- 핵심 수치: 약 24~30px, 500~650
- 섹션 제목: 약 13~16px, 500~600
- 본문·행 정보: 약 11.5~14px
- 보조 메타: 약 10.5~12px
- 행간: 한 줄 요소는 약 1.25, 두 줄 설명은 약 1.4 이상

TrafficVisson 적용 규칙:

- 한글 본문, 제목, 버튼, 배지는 `SUIT Variable`을 사용한다.
- JetBrains Mono는 시간코드, 해시, 모델 버전, ID, 코드명처럼 실제로 정렬이 필요한 기술 토큰에만 사용한다.
- 한국어 문장 전체를 모노 폰트로 표시하지 않는다.
- 1280×720 기본 화면에서 본문은 12px 미만으로 축소하지 않는다. 주요 조작은 13~14px 이상을 유지한다.
- 좁은 행에 맞추기 위해 글자를 자르지 않는다. 콘텐츠 우선순위, 열 축약, 2행 배치를 먼저 사용한다.

### 2.5 밀도와 여백

참조는 한 화면에 정보가 많지만 빈 공간이 기능적이다.

- 큰 빈 패널이 아니라 카드 내부의 호흡 공간이 있다.
- 바깥 셸과 콘텐츠 사이 여백은 크고, 카드 사이는 상대적으로 촘촘하다.
- 숫자, 상태, CTA의 묶음이 시각적으로 분명하다.
- 같은 레벨의 카드 수를 줄이고 크기를 달리해 시선 흐름을 만든다.
- 스크롤을 전제로 세로로 카드를 쌓지 않는다.

### 2.6 참조에서 가져오면 안 되는 것

- 금융 서비스의 텍스트와 장식용 수치
- 사람 얼굴 아바타
- 원형 잔액 버블을 도로 데이터와 무관하게 그대로 복제하는 것
- 1200×900 캔버스 비율
- 실제 아이콘 대신 텍스트 기호를 사용하는 것
- 모든 패널에 무거운 blur를 거는 것

TrafficVisson에서는 원형 버블의 역할을 “분석 진행의 핵심 단계”, “승인 사건”, “현재 모델 상태” 같은 실제 데이터 표현으로 치환할 수 있지만, 단순 장식으로 사용하면 안 된다.

## 3. HTML이 의도한 제품 화면

### 3.1 전역 셸

HTML의 설계 좌표:

- 고정 아트보드: 1920×1080
- 상단 앱 바: 50px
- 하단 작업 상태 바: 42px
- 중앙 여백: 12px
- 왼쪽 화면 내비게이션: 262px
- 화면 간 기본 간격: 12px
- 선택형 개발 스펙 패널: 338px
- 주 카드 반경: 22px
- 내비게이션/버튼: `border-radius: 999px`
- 주 글자: 15px
- 화면 제목: 25px, weight 640
- 일반 본문/버튼: 13~14.5px
- 메타/코드: 11.5~12.5px JetBrains Mono
- 유리 패널: 흰색 0.46~0.72, `blur(30~40px)`, `saturate(170~200%)`, 1px 흰 테두리, 청보라 그림자

이 구조의 의도는 명확하다.

1. 상단에는 제품, 현재 프로젝트, 장치/Provider 상태가 있다.
2. 왼쪽에는 9개 업무 화면이 항상 보인다.
3. 중앙은 한 시점에 한 업무만 수행한다.
4. 하단에는 장시간 작업의 진행 상태가 고정된다.
5. 오른쪽 스펙 패널은 화면 ID, API, 엔터티, 규칙을 확인하는 개발용 보조 영역이다.

제품 구현에서는 오른쪽 스펙 패널을 일반 사용자 기본 화면에 노출하지 않아야 한다. 1280×720에서 338px를 상시 점유하면 핵심 업무가 무너진다. 진단/개발 모드의 별도 드로어가 적합하다.

### 3.2 9개 화면의 정보 구조

#### 16.1 프로젝트 홈

- 프로젝트 열기/생성
- 분석 진행, 검토 대기, 심각·긴급 사건, 활성 모델, 보고서 상태
- 최근 주행 표
- 질문 큐
- 첫 실행 점검 상태

의도: 사용자가 다음 행동을 5초 안에 찾게 하는 운영 허브.

주의: HTML은 같은 비중의 상단 KPI를 여럿 배치한다. 참조 PNG와 최신 루트 계획의 방향은 비대칭 핵심 카드다. 구현은 참조 PNG 쪽 위계를 우선해야 한다.

#### 16.2 영상 가져오기

- 로컬 MP4/MOV, GPX
- URL과 지원 등급
- 메타데이터 검사
- 권리 확인
- 다운로드/해시/보안 검사
- 첫 프레임과 GPS 오프셋 비교

의도: 입력을 받는 폼이 아니라, 안전성·권리·위치 동기화를 확인하는 검증 작업대.

#### 16.3 질문형 라벨링

- 학습 보조/전수 검토/빠른 검토
- 대표 프레임과 AI 박스
- 앞뒤 프레임 스트립
- 지도 위치
- 질문, 유형, 심각도, 신뢰도
- 예/아니오/판단 어려움/영역 수정
- 유형 변경/고급 편집/건너뛰기
- 유형별 초기 표본 진행률

의도: 사용자가 모든 프레임에 박스를 직접 그리지 않고 질문에 답해 라벨을 확정.

#### 16.4 분석

- 작업 로그
- 일시정지/취소/복구

의도: 장시간 로컬 작업의 신뢰와 복구 가능성을 보여 주는 상태 화면.

#### 16.5 사건 검토

- 영상 오버레이와 주행 영역
- AI 원본/사용자 최종/비식별화 전환
- 병합·분리 근거
- OCR·위치 검증
- AI/답변/최종값 비교
- 승인/반려/학습 제외/추가 흐림

의도: AI 제안과 최종 판정을 덮어쓰지 않고 나란히 검증.

#### 16.6 모델 관리

- 학습 가능 게이트
- 클래스 분포
- 활성 v7/후보 v8 비교
- 유형별 recall/precision/중복률
- 모델 카드
- 학습, 승격, 거부, 롤백

의도: “새 모델이 있다”가 아니라 기존 모델보다 안전한지 사용자가 확인.

#### 16.7 GPS 히스토리

- 영상
- 지도 경로와 현재 차량
- 속도 0.5/1/2/4배
- 재생/5초 탐색/스크럽
- GPS 누락 구간
- 사건 타임라인과 목록
- 동일 사건 증거 카드

의도: `playback_time_ms` 하나로 지도, 영상, 타임라인, 목록, 증거를 동기화.

#### 16.8 보고서

- HWP COM/Codex/Claude 상태
- 외부 모델로 보낼 데이터 범위
- `DocumentEditPlan`
- 항목별 수락/거절
- 한/글 문서 페이지 미리보기
- 적용/롤백/HWPX/HWP 저장

의도: 언어모델이 문서를 직접 쓰지 않고 구조화 편집 계획을 검토한 뒤 결정적 COM 편집기로 적용.

#### 16.9 내보내기

- 프로젝트 디렉터리 트리
- CSV 규칙
- Trip Package 포함 항목
- 산출물 행 수, 크기, SHA-256, 생성 주체
- 공유용 비식별화 상태

의도: 결과 파일을 “생성됨”으로 끝내지 않고 출처와 무결성까지 이해.

- 프로젝트 열기/새 프로젝트

- URL 검사·다운로드·등록
- GPS 동기화 확정
- 질문 유형 변경, 고급 편집기, 건너뛰기

- 사건 이전/다음, 분리, 대표 캡처, 승인/반려

- 실제 HWP COM 적용, 저장
- 내보내기

즉 HTML은 제품의 시각·정보 설계 증거이지 기능 완성 증거가 아니다.

### 3.5 HTML을 제품 코드로 재사용하면 안 되는 이유

1. 1920×1080 고정 크기라 1280×720에서 자연스럽게 재배치되지 않는다.
2. Pretendard와 JetBrains Mono가 외부 CDN에 의존한다.
3. `support.js`가 React와 ReactDOM을 `unpkg.com`에서 실행 중 로드한다.
4. 생성된 DC runtime은 Electron 제품의 main/preload/renderer 보안 경계가 아니다.
5. 실제 기능이 없는 클릭 가능 `div`가 많다.
6. 접근 가능한 버튼·라벨·포커스 의미 구조가 부족하다.
7. 여러 화면이 동시에 여러 `overflow-y:auto` 영역을 가진다.
8. 30~40px backdrop blur를 많은 카드에 반복해 저사양 Windows GPU에서 페인트 비용이 커질 수 있다.
9. 영상·지도·증거 영역이 줄무늬 placeholder라 실제 데이터 밀도와 가독성이 검증되지 않았다.

## 4. 업로드 계획서와 루트 계획서의 관계

### 4.1 권위 판정

업로드 계획서의 첫 네 줄이 스스로 다음을 선언한다.

- `역사적 v2.0 보관본`
- `현재 구현 기준으로 사용하지 않음`
- 현재 단일 기준본은 루트 계획서
- 본문 현재형 표현은 현재 상태가 아님

다만 링크 라벨이 `v2.7`로 남아 있어 현재 루트 `v2.9`와 어긋난다. 이 값은 역사적 포인터가 갱신되지 않은 것이다.

`git diff --no-index` 기준으로 루트 v2.9는 업로드 v2.0에 비해 351줄을 추가하고 29줄을 변경했다. 두 문서의 목표 제품 구조는 대체로 같지만, 루트 문서는 실제 알파 구현·제약·검증 결과를 추가해 과장된 완료 해석을 막는다.

### 4.2 업로드 문서에서 여전히 유효한 목표

- Windows Electron 설치형 단일 제품
- renderer/main/loopback bridge 보안 경계
- 로컬/링크/GPX 입력
- 12개 표준 사건 유형
- 낙하물 강제 질문
- 차선/색깔유도선/식생 관계 판정
- 질문형 라벨링과 영역 수정
- 프로젝트별 데이터셋·모델 격리
- 지도·영상·타임라인·목록 동기화
- 7개 CSV, JSON, Trip Package, provenance
- HWP/HWPX COM 편집 계획
- Codex·Claude Provider와 비활성 로컬 모델 슬롯
- 9개 사용자 화면
- 보안·성능·모델·HWP 종단 테스트
- M0~M11 마일스톤
- 최종 완료 정의 19개

이 항목들은 삭제 대상이 아니라 루트 v2.9의 목표 사양으로 계속 유지할 체크리스트다.

### 4.3 현재 상태와 충돌하거나 역사적 상태인 부분

| 업로드 v2.0/HTML 표현 | 현재 해석 |

| `YOLO26s-seg 1280px`가 초기 모델 | 아직 목표 후보. 현재 번들 검토 보조는 고정 Grounding DINO Tiny Q4 ONNX |
| Python 3.12 임베디드 | 목표. 현재 frozen bridge는 Python 3.9.13이라 교체 필요 |
| GPX 경로와 MapLibre 동기화 | 미구현. 현재 좌표는 촬영 시작 위치뿐 |

| 1920×1080 고정 HTML | 1280×720 한 화면 작업대가 실제 기본 검증 크기 |

## 5. 구현 검증 체크리스트

이 체크리스트는 “화면이 비슷해 보인다”가 아니라 실제 제품의 시각·업무·저장 결과를 함께 검증하도록 구성했다.

### 5.1 시각 기준 P0

- [ ] Electron 창 내부에 다시 큰 브라우저/웹페이지 모양의 외곽 카드가 없다.
- [ ] Windows 네이티브 caption 영역을 제외한 앱 콘텐츠가 창의 가용 영역을 직접 사용한다.
- [ ] 기본 1280×720에서 `documentElement.scrollHeight === clientHeight`다.
- [ ] 모든 화면의 제목, 주요 수치, CTA, 배지가 위아래로 잘리지 않는다.
- [ ] 한글 본문 computed font가 로컬 번들 `SUIT Variable`이다.
- [ ] 외부 Pretendard/Google Fonts/Unpkg CDN 없이 오프라인 패키지에서 같은 화면이 나온다.
- [ ] 한 화면에 동일 비중의 KPI 카드만 네 개 이상 반복하지 않는다.
- [ ] 홈에 한 개의 분명한 포컬 영역과 그보다 작은 보조 영역이 있다.
- [ ] 검은 기본 CTA는 한 화면의 가장 중요한 행동 하나에만 사용한다.
- [ ] 실제 이미지·지도·아이콘을 사용하며 줄무늬 placeholder, 텍스트 기호, 이모지, 임의 SVG 지도를 최종 화면에 남기지 않는다.

### 5.2 타이포그래피·가독성 P0

- [ ] 일반 한글 본문 12px 이상, 주요 버튼/행 13px 이상, 화면 제목 22~26px 범위다.
- [ ] 본문 line-height는 최소 1.35이고 두 줄 설명은 1.4 이상이다.
- [ ] JetBrains Mono는 ID, 해시, 시간코드, 모델 버전, 영문 코드에만 사용한다.
- [ ] 중요 한글 문장을 `text-overflow: ellipsis`로 숨기지 않는다.
- [ ] 200% Windows 배율에서도 핵심 조작과 상태가 읽힌다.
- [ ] 밝은 유리 배경 위 일반 텍스트가 4.5:1 수준의 대비를 갖는다.
- [ ] 상태를 색만으로 구분하지 않고 텍스트·형태를 함께 제공한다.

### 5.3 표면·그리드 P1

- [ ] 화면 배경은 순백이 아니라 차가운 회청색 계열이다.
- [ ] 주 업무 열과 보조 열의 비중이 약 65:35이며 화면 목적에 따라 비대칭이다.
- [ ] 주요 카드 반경은 18~22px, 작은 칩은 6~10px, 알약형 조작만 999px다.
- [ ] 카드 사이 기본 간격은 10~14px, 구조적 열 간격은 그보다 크다.
- [ ] 유리 카드는 내용이 읽힐 만큼 충분히 불투명하다.
- [ ] 테두리는 1px 밝은 하이라이트, 그림자는 저채도 청보라 계열이다.
- [ ] 강한 파랑/보라 그래디언트는 한 화면의 한두 포컬 요소에만 사용한다.
- [ ] 같은 깊이의 카드가 세 겹 이상 중첩되지 않는다.
- [ ] 전역 blur는 셸/큰 표면 중심으로 제한하고 작은 카드마다 30~40px blur를 반복하지 않는다.

### 5.4 스크롤·반응형 P0

- [ ] 1280×720, 1600×900, 1920×1080 세 크기에서 각각 새로 캡처한다.
- [ ] 각 화면의 바깥 문서에는 세로 스크롤이 없다.
- [ ] 한 작업 화면에서 동시에 보이는 내부 세로 스크롤은 최대 한 곳이다.
- [ ] 스크롤 영역은 경계와 고정 헤더/고정 CTA를 가져 소유권이 명확하다.
- [ ] 라벨링에서는 질문, 네 답변, 건너뛰기, 현재 증거가 첫 화면에 함께 보인다.
- [ ] 작은 화면에서 스펙/진단 패널은 기본 숨김이다.
- [ ] 열을 줄일 때 먼저 보조 메타를 접고, 글자를 8~10px로 축소하지 않는다.

### 5.5 홈

- [ ] 현재 프로젝트와 다음 행동이 5초 안에 식별된다.
- [ ] 분석 진행/검토 대기/심각 사건/모델/보고서 중 하나가 주 포컬 카드다.
- [ ] 나머지 상태는 작은 카드·목록·배지로 계층화된다.
- [ ] 최근 주행과 다음 질문은 실제 저장소 값이다.
- [ ] 빈 상태에서는 가짜 100%, 가짜 사건, 가짜 활성 모델을 표시하지 않는다.
- [ ] 새 프로젝트, 프로젝트 열기, 라벨링 시작이 실제 화면 전환과 저장 결과로 이어진다.

### 5.6 영상 가져오기

- [ ] 로컬 파일과 UNC 파일 선택이 main process의 안전한 파일 핸들로 동작한다.
- [ ] URL은 지원 등급·권리 확인·검사 상태를 실제 결과와 함께 표시한다.
- [ ] 미구현 공급자 다운로드는 성공처럼 보이지 않고 명시적으로 비활성/준비 중이다.
- [ ] MIME/magic, 크기, duration, SHA-256, 저장 위치가 실제 값이다.
- [ ] GPX가 없으면 동기화 UI와 지도 경로가 가짜 데이터를 만들지 않는다.
- [ ] 다운로드/해시 진행률은 작업 상태에서 갱신되며 일시정지·취소가 실제로 동작한다.

### 5.7 질문형 라벨링

- [ ] 사용자 자연어 명령이 지원 사건 유형 하나의 고정 recipe로 해석된다.
- [ ] AI 결과는 `review-only`임을 화면에서 분명히 표시한다.
- [ ] 대표 프레임, AI 박스/마스크, 전후 프레임, 2~5초 클립, 위치가 같은 후보를 가리킨다.
- [ ] `예`는 승인 라벨, `아니오`는 hard negative, `판단 어려움`은 학습 제외 보류, `영역 수정`은 새 geometry revision을 만든다.
- [ ] 답변 직후 `question_id`, AI 원본, 최종 영역, 답변 revision, 감사 해시가 저장된다.
- [ ] 낙하물과 긴급 후보는 모든 정책에서 질문 큐에 남는다.
- [ ] 같은 사건의 연속 프레임이 여러 질문으로 중복되지 않는다.
- [ ] 사용자가 답하지 않은 AI 제안은 Incident·학습·모델 승격으로 자동 이동하지 않는다.

### 5.8 분석

- [ ] 현재 단계와 전체 15단계 중 위치가 명확하다.
- [ ] 처리 프레임, 원시 검지, 사건 병합, 예상 시간은 실제 작업 데이터다.
- [ ] GPU/CPU fallback과 점수 의미가 솔직하게 표시된다.
- [ ] 취소·재개·오류 복구가 마지막 완료 단계에서 실제로 이어진다.
- [ ] 로그 영역 하나만 내부 스크롤을 소유하고 주요 상태·취소 조작은 고정된다.
- [ ] 1시간 영상 ≤ 2시간 목표는 측정된 실제 테스트로만 통과시킨다.

### 5.9 사건 검토

- [ ] AI 원본, 사용자 답변, 최종값을 덮어쓰지 않고 나란히 비교한다.
- [ ] 영상 오버레이와 증거 카드가 같은 `incident_id`와 타임코드를 가리킨다.
- [ ] 병합/분리 규칙과 ReviewAction 이력이 보인다.
- [ ] OCR 원문, 정규화 이름, GPS 검증 상태가 분리돼 있다.
- [ ] 승인/반려/학습 제외/추가 흐림이 저장소 상태에 반영된다.
- [ ] 원본/AI 표시/사용자 최종/공유본/클립을 실제 파일로 확인할 수 있다.

### 5.10 모델 관리

- [ ] 새 확정 라벨 100건과 유형별 검증 30건을 실제 데이터로 계산한다.
- [ ] 조건 미충족 시 학습 버튼은 비활성이고 원인을 표시한다.
- [ ] 학습 전에 시간, VRAM, 디스크, 클래스 분포를 보여 준다.
- [ ] 같은 고정 검증 세트로 기존 모델과 후보 모델을 비교한다.
- [ ] recall −2%p 이상 하락, 오탐/중복 증가 시 승격을 차단한다.
- [ ] 승격, 거부, 롤백은 실제 모델 카탈로그와 활성 버전에 반영된다.
- [ ] 프로젝트 A의 라벨·모델이 프로젝트 B에 섞이지 않는다.

### 5.11 GPS 히스토리

- [ ] GPX 또는 시간대별 GPS가 없으면 가짜 경로를 그리지 않는다.
- [ ] GPS가 있을 때 재생 시간에 따라 진행선이 이동 방향으로 채워진다.
- [ ] 영상, 지도, 타임라인, 사건 목록, 증거 카드가 하나의 `playback_time_ms`를 공유한다.
- [ ] 마커/목록/타임라인 어느 곳을 눌러도 같은 사건과 영상 시각으로 이동한다.
- [ ] 0.5/1/2/4배, 재생/정지, ±5초, 스크럽이 모두 동기화된다.
- [ ] 10초 초과 누락은 점선과 `GPS_MISSING`으로 표시하며 직선 보간하지 않는다.
- [ ] 수동 오프셋 후 영상·지도 시각차가 2초 이하인지 측정한다.

### 5.12 보고서

- [ ] HWP COM이 없으면 기능을 비활성화하고 설치/등록 원인을 표시한다.
- [ ] Codex/Claude 상태는 공식 CLI의 상태만 읽고 인증 파일을 직접 읽지 않는다.
- [ ] 외부 전송 전 승인 사건 JSON, OCR, 비식별화 이미지, 문서 구조 요약을 보여 준다.
- [ ] 원본 영상과 원본 개인정보가 전송 목록에 포함되지 않는다.
- [ ] LLM 출력이 `DocumentEditPlan` 스키마를 통과하지 않으면 COM 쓰기를 시작하지 않는다.
- [ ] 항목별 수락/거절/전체 롤백이 실제 작업본에 반영된다.
- [ ] 저장 후 재열기와 모든 페이지 렌더로 표 잘림, 사진 누락, 넘침을 확인한다.
- [ ] 이미지·지도·표·문단 서식이 사용자 양식에서 보존된다.

### 5.13 내보내기

- [ ] 7개 CSV, `report_payload.json`, `manifest.json`을 생성한다.
- [ ] CSV는 UTF-8 BOM, ISO 8601, 영상 타임코드, AI/사용자 최종 분리 열을 갖는다.
- [ ] 정확히 선택한 분석 작업의 active·approved Incident만 확정 산출물에 포함한다.
- [ ] 모든 파일의 행 수, 크기, SHA-256, 생성 주체가 manifest와 일치한다.
- [ ] 승인 사건의 JPEG/MP4 증거가 올바른 `incident_id` 아래 연결된다.
- [ ] 원본 영상은 기본 제외다.
- [ ] 공유 패키지는 얼굴·번호판 비식별화 파생본만 포함한다.

### 5.14 접근성·키보드

- [ ] 모든 클릭 가능한 `div`를 의미 있는 `button`, `a`, `input` 등으로 구현한다.
- [ ] 키보드만으로 왼쪽 화면 이동, 질문 답변, 사건 선택, 보고서 수락/거절이 가능하다.
- [ ] 포커스 링이 유리 배경에서도 분명하다.
- [ ] 아이콘 전용 버튼에 접근 가능한 이름과 툴팁이 있다.
- [ ] 재생·작업 진행·오류 같은 상태 변화가 보조기술에 전달된다.
- [ ] 32×32px보다 작은 핵심 클릭 목표가 없다.
- [ ] 스크린샷만으로 WCAG 준수를 선언하지 않고 DOM·키보드·스크린리더를 별도 시험한다.

### 5.15 성능

- [ ] 정지 화면에서 지속적인 layout/paint가 없다.
- [ ] 경로 애니메이션은 transform/전용 레이어를 우선하고 큰 blur 영역을 매 프레임 다시 그리지 않는다.
- [ ] 1280×720의 GPS 재생이 55fps 이상을 안정적으로 유지한다.
- [ ] 클릭/질문 답변의 시각 응답이 100ms 안에 시작된다.
- [ ] 긴 목록은 가상화하거나 제한 조회하며 DOM 노드를 무한히 쌓지 않는다.
- [ ] 이미지·클립은 현재 사건 주변만 로드하고 이전 object URL을 해제한다.
- [ ] reduced motion 환경에서 불필요한 펄스·경로 애니메이션을 줄인다.
- [ ] 배터리/GPU가 제한된 Windows 환경에서 backdrop-filter 축소 모드를 제공한다.

## 6. 블라인드 비교 합격 절차

최종 시각 판정은 화면 캡처 한 장을 저장하는 것으로 끝내지 않는다.

1. 현재 실행 앱을 1280×720에서 새로 캡처한다.
2. 참조 PNG, HTML `.thumbnail`, 현재 화면을 같은 높이로 한 비교 이미지에 나란히 둔다.
3. 다음 10개 항목을 0/1/2점으로 평가한다.
   - 단일 창형 제품 인상
   - 비대칭 위계
   - 큰 포컬 카드
   - 차분한 청회색 재료
   - 강조색 절제
   - SUIT 가독성
   - 카드 밀도
   - 일관된 반경·간격
   - 핵심 조작 가시성
   - 잘림·스크롤 없음
4. 18/20 이상이면서 P0가 0건이어야 시각 후보 통과다.
5. 9개 화면 전체에서 P0/P1/P2를 기록하고 수정한다.
6. 수정 후 동일 viewport와 동일 데이터 상태로 다시 비교한다.
7. 실제 기능 테스트, 접근성, 성능 검증이 별도로 통과해야 한다.
8. 최종 `design-qa.md`는 실제 근거 경로와 함께 정확히 `final result: passed`를 기록해야 한다.

픽셀 차이는 콘텐츠가 다른 FundFlow 참조와 TrafficVisson 사이의 올바른 지표가 아니다. 대신 셸 비율, 주/보조 열 비율, 카드 크기 위계, 글자 크기, 반경, 간격, 색상 사용량 같은 시각 랜드마크를 비교한다.

## 7. 바로 적용할 우선순위

### P0

1. 단일 Electron 창과 1280×720 무문서스크롤을 고정한다.
2. 모든 잘림과 12px 미만 본문을 제거한다.
3. SUIT Variable 로컬 번들을 전 화면 computed font로 검증한다.
4. 홈의 동일 KPI 카드 반복을 비대칭 포컬 구조로 바꾼다.
5. 라벨링 질문·증거·네 답변을 같은 첫 화면에 고정한다.
6. 보이는 핵심 CTA를 실제 업무·저장 결과에 연결하거나 솔직한 비활성 상태로 바꾼다.

### P1

1. 유리 표면 수와 blur 비용을 줄인다.
2. 개발 스펙 패널을 기본 사용자 화면에서 제거한다.
3. JetBrains Mono의 한글 사용을 제거한다.
4. 9개 화면의 시각 위계를 같은 재료 체계로 통일한다.
5. 실제 지도·영상·증거가 들어왔을 때의 밀도와 대비를 재검증한다.

### P2

1. 포커스, 키보드, 툴팁, 빈 상태를 정리한다.
2. 상태 칩의 높이와 baseline을 통일한다.
3. motion과 reduced-motion을 정리한다.
4. 1600×900, 1920×1080에서 여백이 과하게 늘어나지 않도록 최대 작업 폭을 조정한다.

## 8. 감사 한계

- 참조 PNG는 정적 이미지이므로 실제 폰트 파일, blur 수치, 접근성 의미 구조를 확정할 수 없다.
- `.thumbnail`은 축소 WebP라 미세 타이포·경계선 검증용이 아니다.
- HTML의 상호작용은 소스 상태 변경을 기준으로 판정했으며 실제 Electron IPC나 브리지 동작을 뜻하지 않는다.
- 업로드 계획서의 구현 상태는 역사적 문서라 현재 증거로 사용하지 않았다.
- 이 문서는 디자인 폴더 포렌식만 담당한다. 현재 Electron 화면의 새 캡처와 실제 성능 측정은 별도 현재 실행 감사에서 완료해야 한다.
